# Tendermint의 블록 제안과 투표

상태: 초안 · 공개 프로토콜 기준

## 핵심 질문

Tendermint는 여러 검증자가 어떤 블록을 정식 블록으로 채택할지 결정한다. 애플리케이션이
트랜잭션을 실행하는 일과, 검증자들이 블록에 합의하는 일은 구분해야 한다.

## 전체 흐름

```text
Propose → Prevote → Precommit → Commit
```

### Propose

각 높이와 라운드에는 proposer가 정해진다. proposer는 자신이 받은 트랜잭션을 블록으로
묶어 제안한다.

```text
Block N
├─ header
├─ transaction 1
└─ transaction 2
```

### Prevote

검증자는 제안 블록의 구조와 합의 규칙을 확인한다. 유효한 후보라고 판단하면 블록 ID에
prevote를 보내고, 잘못됐거나 제때 받지 못하면 `nil`에 투표할 수 있다.

```text
Validator A → Prevote(Block X)
Validator B → Prevote(Block X)
Validator C → Prevote(nil)
```

여기서 찬성은 트랜잭션 하나하나에 대한 찬성이 아니라 현재 높이·라운드의 블록 후보를
인정한다는 뜻이다.

### Precommit

충분한 prevote가 모이면 검증자는 해당 블록에 precommit을 보낸다.

```text
Block X에 충분한 prevote
        ↓
Block X에 대한 precommit
```

### Commit

검증자 지분 기준으로 2/3를 초과하는 precommit이 모이면 블록이 확정된다.

```text
Block X + 2/3 초과 voting power의 precommit
                  ↓
               Commit
```

## 검증자가 확인하는 것

```text
블록 높이가 맞는가?
이전 블록 해시와 연결되는가?
제안자가 해당 라운드의 proposer인가?
헤더와 데이터의 해시가 일치하는가?
블록 크기와 합의 파라미터를 지키는가?
투표와 서명이 유효한가?
```

블록에 포함된 트랜잭션 하나가 실행에 실패할 수는 있지만, 그 사실만으로 블록 전체가
무효가 되는 것은 아니다. 블록이 합의 규칙에 맞으면 실패한 트랜잭션의 상태 변경만
반영되지 않을 수 있다.

## Voting power와 2/3

검증자 수가 아니라 voting power의 합으로 기준을 계산한다.

```text
A: 40
B: 35
C: 25
전체: 100
```

A와 B가 같은 블록에 precommit하면 75의 voting power를 얻는다. 이는 2/3를 넘으므로
블록을 확정할 수 있다.

1/3 미만의 악성 지분을 가정하는 이유도 여기에 있다. 정직한 검증자가 같은 높이와
라운드에서 서로 다른 두 블록에 동시에 서명하지 않는다면 서로 다른 두 블록이 각각
2/3의 precommit을 얻기는 어렵다.

## 투표 서명

투표 서명은 단순히 블록 해시만 서명하는 것이 아니다. 보통 체인 ID, 높이, 라운드, 투표
종류, 블록 ID 같은 문맥이 함께 서명 대상이 된다.

```text
chain ID + height + round + step + block ID
                     ↓
                  서명
```

따라서 다른 체인이나 다른 높이의 투표를 재사용하기 어렵다.

## 라이트 클라이언트와 커밋

라이트 클라이언트는 전체 블록을 다시 실행하지 않고, 신뢰하는 헤더와 검증자 커밋을
확인할 수 있다.

```text
블록 헤더
+ 충분한 검증자 서명
→ 이 블록이 합의되었다는 증명
```

검증자 세트가 바뀌면 새 세트도 이전 세트가 승인한 변경인지 확인해야 한다.

## 정리

```text
Propose: proposer가 블록 제안
Prevote: 유효한 후보인지 투표
Precommit: 확정 방향의 투표
Commit: 2/3 초과 voting power 확보 후 확정
```

## 찬성의 기준을 더 구체적으로 보기

검증자가 `Block X`에 찬성한다는 것은 트랜잭션 각각의 사업적 결과에 찬성한다는 뜻이
아니다. 현재 높이와 라운드에서 이 블록을 합의 대상으로 인정할 수 있다는 뜻이다.

```text
블록 높이와 라운드가 맞는가?
이전 블록 hash와 연결되는가?
이번 라운드의 proposer가 제안했는가?
헤더와 트랜잭션 데이터의 커밋이 일치하는가?
블록 크기와 합의 파라미터를 지키는가?
투표 서명이 유효한가?
```

애플리케이션 트랜잭션이 실행 중 실패할 수 있다는 사실과 블록 자체가 합의 규칙을 지키는
것은 별개다. 예를 들어 블록에 잔액 부족 트랜잭션이 들어 있어도 블록 구조와 합의 조건이
유효하면 블록은 확정되고 해당 트랜잭션의 상태 변경만 실패할 수 있다.

## 블록 크기와 투표

트랜잭션 크기는 객체가 아니라 직렬화된 바이트 길이로 계산한다. 블록의 `max_bytes`는
헤더·트랜잭션·evidence를 포함한 전체 크기 제한이고, `max_gas`는 실행량 제한이다.

```text
max_bytes - 헤더와 오버헤드 = tx에 사용할 수 있는 공간
```

바이트 공간이 남아 있어도 블록의 `max_gas`를 초과하면 트랜잭션을 더 포함할 수 없다.
실제 파라미터는 네트워크의 genesis와 이후 합의 파라미터 업데이트가 정한다.

## 검증자 세트 변경

현재 블록을 확정할 때는 현재 검증자 세트를 사용하고, 블록 실행 중 계산된 검증자 업데이트는
블록 경계 뒤에 적용한다.

```text
Block N 합의: 기존 세트
Block N EndBlock: 변경 결과 계산
Block N+1 합의: 새 세트
```

검증자 수가 아니라 지분 가중치가 기준이므로, 지분이 큰 한 검증자가 여러 작은 검증자보다
더 큰 voting power를 가질 수 있다. 같은 높이와 라운드에서 서로 다른 블록에 서명하는
이중 서명은 검증 가능한 증거가 되며 슬래싱 대상이 될 수 있다.
