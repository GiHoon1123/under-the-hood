# 블록체인 기초 개념 심화 복습 노트

상태: 대화 내용 확장 기록 · 공개 프로토콜 기준

이 문서는 앞선 문서에서 축약한 질문과 예시를 복습용으로 다시 적은 것이다. 회사 비공개
저장소의 경로·파일명·내부 함수명은 사용하지 않고 공개 개념으로 설명한다.

## 결정성과 상태 머신

블록체인의 상태에는 잔액뿐 아니라 계정 nonce, 계약 코드와 storage, 검증자와 voting power,
거버넌스 설정이 포함된다. 상태를 `Sₙ`, 블록을 `block`, 상태 전이 규칙을 `F`라고 하면
`F(Sₙ, block) → Sₙ₊₁`로 표현할 수 있다.

예를 들어 `Sₙ = { Alice: 100, Bob: 50 }`이고 블록에 `Alice → Bob : 20`이 있으면 다음
상태는 `{ Alice: 80, Bob: 70 }`이다. 모든 노드가 같은 이전 상태와 같은 트랜잭션 순서를
사용하면 반드시 같은 결과를 계산해야 한다.

합의는 어떤 블록을 선택할지를 정할 뿐, 선택된 블록을 노드마다 다르게 실행하는 문제를
해결하지 않는다. 그래서 상태 전이 코드는 결정적이어야 한다.

## 결정성을 깨뜨리는 입력

현재 시간을 직접 읽으면 노드의 시계와 실행 시점이 달라질 수 있다. 합의된 블록 timestamp를
사용해야 한다.

일반 난수 생성기를 호출하면 노드마다 다른 값이 나올 수 있다. 랜덤성이 필요하면 블록 해시
같은 공통 입력으로 결정적인 값을 계산해야 한다.

운영체제별 경로·시간·정수 처리나 시스템 호출 결과를 상태 전이에 직접 사용하면 플랫폼별
상태가 생길 수 있다.

Go map 순회 순서는 보장되지 않는다. 해시나 직렬화에 사용하려면 키를 정렬해야 한다.

외부 HTTP·DNS·데이터베이스의 응답은 노드마다 다를 수 있다. 외부 데이터는 오라클이나
합의된 메시지로 먼저 기록해야 한다.

부동소수점은 십진수를 정확히 표현하지 못할 수 있다. 토큰은 최소 단위의 정수로 처리한다.
정렬되지 않은 이벤트나 key 목록도 처리 전에 정렬 규칙을 정해야 한다.

## ABCI와 실행 단계

ABCI는 Tendermint의 블록 제안·투표·합의와 애플리케이션의 트랜잭션 검사·실행·상태 저장을
연결한다.

`CheckTx`는 합의 전 트랜잭션을 mempool에 넣어도 되는지 검사한다. 성공했다고 확정된 것은
아니다. 다른 트랜잭션이 먼저 잔액이나 nonce를 바꿀 수 있다.

`DeliverTx`는 확정된 블록의 트랜잭션을 정해진 순서로 실행한다. `tx1`이 잔액을 사용하면
`CheckTx`를 통과한 `tx2`도 `DeliverTx`에서 실패할 수 있다.

실행 순서는 `BeginBlock → DeliverTx → EndBlock → Commit`이다. BeginBlock은 블록 컨텍스트와
제한을 준비하고, EndBlock은 검증자 업데이트와 블록 후처리를 수행하며, Commit은 성공한
상태를 저장하고 상태 커밋을 반환한다.

## Prevote의 찬성 기준

검증자는 트랜잭션 하나가 아니라 블록 ID에 투표한다. 이전 블록 연결, 높이와 라운드,
proposer, 헤더·데이터, 블록 크기, 투표 서명 등을 확인한 뒤 유효한 후보면 `Prevote(Block X)`,
그렇지 않으면 `Prevote(nil)`을 보낼 수 있다.

충분한 prevote 후 precommit을 보내고, 2/3 초과 voting power의 precommit이 모이면 블록이
확정된다. 기준은 검증자 수가 아니라 지분 가중치다.

## 블록과 트랜잭션 크기

트랜잭션 크기는 메모리 객체 크기가 아니라 protobuf나 RLP 등으로 직렬화한 bytes의 길이다.
블록 크기는 헤더·트랜잭션·evidence·기타 오버헤드를 포함한다. `max_bytes`는 바이트 제한,
`max_gas`는 실행량 제한이며 서로 다른 합의 파라미터다. 실제 값은 genesis와 파라미터
업데이트로 정해진다.

## Gas와 rollback

gasLimit은 최대 실행량이고 gasUsed는 실제 실행량이다. 일반적인 수수료는
`gasUsed × 유효 gas price`로 계산한다. 블록에 max_gas가 있으면 바이트 공간이 남아도
실행량 때문에 트랜잭션을 더 넣지 못할 수 있다.

실행 중에는 snapshot이나 임시 상태에 변경을 기록한다. 성공하면 Commit에 반영하고,
revert나 out-of-gas면 상태 변경은 rollback할 수 있다. 이미 사용한 계산 비용은 청구될 수 있다.

## Nonce와 replay attack

현재 nonce가 7이면 nonce 7을 다음 트랜잭션에 사용하고 성공 후 8로 증가한다. nonce 7을
다시 보내면 오래된 트랜잭션이다. nonce 8이 먼저 도착하면 선행 nonce를 기다리거나 거부할
수 있다.

Replay attack은 정상 서명된 메시지를 다른 체인이나 다른 상황에서 재사용하는 공격이다.
chain ID를 서명 대상에 포함하면 체인 A의 트랜잭션을 체인 B에서 검증할 수 없다.

## root 값의 구분

`transactionsRoot`는 블록의 입력 트랜잭션 목록을 대표한다. `stateRoot`는 실행 결과 상태
트리를 대표한다. `appHash`는 애플리케이션 전체 상태의 대표 커밋이다. `blockHash`는 블록
헤더 전체의 식별자다. appHash는 일반적으로 block hash가 아니다.

여러 상태 저장소가 있으면 각 상태 root를 정해진 순서로 결합해 appHash를 만들 수 있다.
트랜잭션이 바뀌면 transactionsRoot와 블록 헤더·blockHash가 바뀌고, 상태가 바뀌면 state
root나 appHash가 바뀐다.

## 캐시와 트리 반영

트리 전체를 캐시에 복사하지 않는다. 필요한 key를 읽고 변경된 값과 경로를 임시 상태에
기록한다. 영구 상태가 Alice 100이고 캐시가 Alice 80이면 실행 중 Alice 조회는 80을
반환해야 한다.

실패하면 캐시를 폐기하거나 snapshot으로 되돌린다. 디스크에 부분적으로 쓴 뒤 복구하는
비용과 원자성 문제를 줄이는 것이 캐시의 중요한 이유다.

## Merkle proof와 root

검증에 필요한 것은 증명 대상 값, root까지의 각 단계에 있는 형제 hash, 왼쪽·오른쪽 위치,
비교 기준 root다. 기준 root는 블록 헤더에서 이미 알 수 있으면 proof에 중복해서 보내지
않아도 된다.

검증자는 leaf에서 시작해 형제 hash를 위치에 맞게 결합하고 root를 재계산한다. 계산한 root와
신뢰하는 root가 같으면 해당 값이 포함됐다고 판단한다. 값이 바뀌면 그 leaf에서 root까지의
hash가 연쇄적으로 바뀌므로 예전 proof는 통하지 않는다.

## 라이트 클라이언트

라이트 클라이언트는 전체 블록체인 상태를 저장하지 않고 신뢰하는 헤더·검증자 커밋·상태
root·필요한 proof만 유지한다. 먼저 헤더와 검증자 서명을 확인하고, 노드에서 값과 proof를
받아 root를 재계산한다.

proof만으로는 부족하다. 악성 노드가 값과 proof를 함께 만들 수 있으므로 기준 root가
신뢰할 수 있어야 한다. 따라서 부트스트랩 헤더와 검증자 세트 검증이 필요하다.

## Ethereum raw transaction

EIP-1559 트랜잭션은 chain ID, nonce, fee 필드, gas limit, to, value, data, access list를
가진다. 서명 전 payload는 `0x02 || RLP(fields)`이고 이를 Keccak-256으로 hash한 뒤 개인키로
서명한다. 서명값은 `yParity`, `r`, `s`로 표현한다.

서명된 raw transaction에는 원래 필드와 서명값이 모두 들어간다. RPC로 hash만 보내는 것이
아니다. 노드는 헥사 디코딩과 RLP 디코딩으로 필드를 복원하고, 서명 필드를 제외한 payload를
다시 만들어 message hash를 재계산한다.

## ECDSA 서명

개인키를 `d`, 곡선 기준점을 `G`, 임시값을 `k`, 메시지 hash를 정수 `z`라고 하면 개념적으로
`R = k × G`, `r = Rₓ mod n`, `s = k⁻¹ × (z + r × d) mod n`을 계산한다.

따라서 `privateKey + messageHash`는 덧셈이 아니라 알고리즘 입력을 줄여 쓴 표현이다.
검증자는 개인키를 보지 않고 공개키와 `(r, s)`로 서명이 맞는지 확인한다. 임시값 `k`를
재사용하면 개인키가 노출될 수 있어 검증된 암호 라이브러리를 사용해야 한다.

## 정정 기록

appHash는 블록 해시가 아니며, raw transaction은 hash를 역산해 복원하는 데이터가 아니다.
raw transaction 안에 원본 필드가 있기 때문에 노드가 디코딩하고 같은 hash를 다시 계산한다.
