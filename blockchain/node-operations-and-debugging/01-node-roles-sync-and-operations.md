# 블록체인 노드 운영과 동기화

상태: 초안 · 공개 운영 개념 기준

## 1. 노드란 무엇인가

노드는 블록체인 네트워크에 참여하는 실행 프로세스다. 역할에 따라 저장 범위와 권한이
다르다.

```text
일반 노드:
  블록·상태 동기화, 검증, RPC

검증자 노드:
  일반 노드 기능 + 블록 제안 + 합의 투표 서명

RPC 노드:
  외부 요청 처리에 집중하고 합의 키를 분리
```

## 2. 프로세스 시작 흐름

```text
프로세스 시작
  ↓
설정과 genesis 읽기
  ↓
노드 키·검증자 키 로드
  ↓
블록·상태 DB 열기
  ↓
P2P와 RPC 시작
  ↓
피어 연결
  ↓
블록·상태 동기화
  ↓
합의 참여 또는 질의 처리
```

노드 시작은 단순히 포트를 여는 일이 아니다. 네트워크, 저장소, 합의, 애플리케이션 상태를
함께 준비해야 한다.

## 3. 키의 분리

노드 키, 검증자 키, 계정 키는 목적이 다르다.

```text
노드 키:
  P2P 네트워크에서 노드 식별

검증자 키:
  prevote·precommit·블록 제안 서명

계정 키:
  사용자 트랜잭션 서명
```

RPC 서버와 검증자 키를 같은 환경에 두면 RPC 침해가 곧 합의 서명 키 유출로 이어질 수 있다.
그래서 검증자 키는 별도 signer나 보안 장치로 분리할 수 있다.

## 4. 저장 데이터

```text
블록 데이터
트랜잭션 결과
상태 트리
검증자 세트
합의 메타데이터
피어 정보
키와 설정
```

블록 저장소와 상태 저장소는 다르다.

```text
블록 저장소:
  과거에 어떤 블록이 있었는가?

상태 저장소:
  현재 계정·계약 상태가 무엇인가?
```

과거 블록을 모두 보관하는 archive 노드와 최신 상태 위주로 운영하는 노드는 필요한 저장량이
다를 수 있다.

## 5. 동기화

새 노드는 피어에게 블록과 상태를 받아 네트워크의 최신 높이에 따라간다.

```text
피어 탐색
  ↓
신뢰할 높이와 헤더 확인
  ↓
블록 다운로드
  ↓
헤더·투표·트랜잭션 검증
  ↓
상태 적용
  ↓
최신 높이 도달
```

전체 동기화는 제네시스부터 모든 블록을 실행한다. 상태 동기화나 snapshot 동기화는 검증된
상태 커밋에서 시작하고 이후 블록만 적용해 시간을 줄일 수 있다.

```text
snapshot height
snapshot state root
신뢰할 블록 헤더
```

이 세 가지가 일치하는지 확인하지 않으면 잘못된 상태에서 노드를 시작할 수 있다.

## 6. RPC 운영

```text
지갑·서비스 → RPC → 노드
```

RPC를 인터넷에 그대로 노출하면 대량 요청, 값비싼 상태 조회, 악성 트랜잭션 제출, DoS에
노출될 수 있다.

```text
인증
rate limit
허용 메서드 제한
읽기 전용 노드 분리
로드 밸런싱
```

## 7. 장애와 모니터링

대표적인 장애 원인은 디스크 부족, 메모리 부족, 피어 부족, 잘못된 genesis, 상태 DB 손상,
키 오류, 시스템 시간 불일치, 네트워크 포트 차단이다.

```text
블록 수신 → 상태 실행 성공 → 디스크 저장 실패 → 최신 높이에서 정지
```

운영 중 확인할 지표:

```text
현재 높이와 네트워크 최신 높이
피어 수
블록 수신·생성 지연
Commit 시간
디스크·메모리 사용량
RPC 오류율
검증자 투표 참여율
```

검증자 노드는 프로세스가 살아 있는 것만으로 충분하지 않다. 실제로 투표에 참여하고
있는지 확인해야 한다.

## 8. 복구

상태 DB가 손상되거나 동기화가 너무 오래 걸리면 검증된 snapshot으로 복구할 수 있다.

```text
snapshot 복원
  ↓
snapshot state root 확인
  ↓
그 이후 블록 동기화
```

## 정리

노드 운영은 애플리케이션을 실행하는 것뿐 아니라 네트워크 연결, 저장소, 동기화, 키 보안,
RPC 노출, 상태 커밋과 투표 참여를 함께 관리하는 일이다.
