# C++ 타입, 메모리, 객체 수명

상태: 기초 정리 완료

## 타입은 무엇을 정하는가

```cpp
int count = 10;
double ratio = 0.5;
bool done = false;
```

타입은 값의 저장 크기와 해석 방법, 허용되는 연산을 정한다. 같은 숫자 `10`이라도 `int`와 `double`은 다른 방식으로 저장된다.

```cpp
sizeof(int)
sizeof(double)
```

로 실제 환경의 크기를 확인할 수 있다. 정확한 크기가 필요한 코드는 `int64_t`, `uint32_t`처럼 고정 폭 정수 타입을 사용한다.

## signed와 unsigned

`int`는 음수와 양수를 모두 표현하고, `unsigned int`는 음수를 표현하지 않는 대신 양수 범위가 커진다. 파일 크기나 버퍼 길이에는 `size_t`를 자주 사용한다.

```cpp
size_t length = buffer_length;
```

시스템 호출처럼 성공한 바이트 수 또는 음수 오류를 함께 표현하는 값은 signed 타입이 필요할 수 있다.

## 메모리와 버퍼

```cpp
char data[1024];
```

이 코드는 연속된 1024바이트 공간을 만든다. 파일을 읽으면 운영체제가 이 공간에 데이터를 쓴다.

```text
읽기 전: [ 빈 공간 ][ 빈 공간 ][ 빈 공간 ]
읽기 후: [  H     ][  E     ][  L ...    ]
```

버퍼는 특별한 저장소가 아니라 데이터를 잠시 담는 메모리 공간이다. `uv_buf_t`는 보통 그 공간의 시작 주소와 길이를 설명하는 구조체다.

```cpp
struct uv_buf_t {
  char* base;
  size_t len;
};
```

`base`가 실제 데이터 공간을 가리키고, `len`이 사용할 수 있는 크기를 뜻한다. `uv_buf_t` 자체에 데이터가 복사되는 것은 아니다.

## 스택과 힙

함수 안의 지역 변수는 보통 자동 저장 기간을 가진다.

```cpp
void run() {
  char data[1024];
} // data의 수명 종료
```

함수가 반환된 뒤 비동기 작업이 `data` 주소를 사용하면 이미 수명이 끝났을 수 있다. 반면 동적으로 확보한 메모리는 작업이 끝날 때까지 별도의 소유권 관리가 필요하다.

```text
동기 작업: 생성 → 작업 완료 → 함수 반환
비동기 작업: 생성 → 작업 등록 → 함수 반환 → 나중에 완료
```

## Node/libuv에서의 수명

Node의 `FSReqBase`, `FSReqPromise` 같은 요청 객체는 libuv 작업이 끝날 때까지 요청 상태와 버퍼·Promise 정보를 유지해야 한다.

```text
요청 객체 생성
  ↓
uv_fs_read() 등록
  ↓
함수 반환
  ↓
작업 완료
  ↓
결과 전달
  ↓
요청 객체 정리
```

## 정리

타입은 메모리를 해석하는 규칙이고, 버퍼는 데이터가 들어갈 연속 공간이다. Node/libuv에서는 비동기 작업이 함수 반환 이후에도 진행되므로 객체와 버퍼의 수명이 특히 중요하다.

## 버퍼를 더 구체적으로 보기

버퍼는 “데이터를 넣어두는 빈 공간”이다. 파일의 내용을 바로 JavaScript 변수에 쓰는 것이 아니라 먼저 메모리 공간을 준비하고, 운영체제가 그 공간에 바이트를 쓴다.

```cpp
char data[5];
```

```text
처음:
[ ? ][ ? ][ ? ][ ? ][ ? ]

파일에서 HELLO를 읽은 뒤:
[ H ][ E ][ L ][ L ][ O ]
```

`uv_buf_t`는 이 공간 자체와 구분해야 한다.

```cpp
struct uv_buf_t {
  char* base;
  size_t len;
};
```

```cpp
char data[1024];
uv_buf_t buffer;
buffer.base = data;
buffer.len = sizeof(data);
```

```text
data          → 실제 바이트가 들어갈 공간
buffer.base   → data의 시작 주소
buffer.len    → 사용 가능한 크기
uv_buf_t      → 위치와 크기를 적어둔 설명서
```

즉 `uv_buf_t` 안으로 데이터가 복사되는 것이 아니다. libuv가 `base` 주소를 보고 실제 버퍼에 결과를 기록한다.

## 비동기 버퍼 수명

다음 코드는 동기 작업이라면 자연스럽지만 비동기 작업에서는 위험할 수 있다.

```cpp
void start() {
  char data[1024];
  start_async_read(data);
}
```

```text
start() 시작
  → data 생성
  → data 주소를 비동기 작업에 전달
  → start() 반환
  → data 수명 종료
  → 나중에 작업 완료
  → 이미 끝난 주소에 쓰려고 할 위험
```

따라서 요청 객체가 버퍼를 소유하거나, 작업 완료까지 버퍼를 유지하는 별도 소유자가 필요하다.

## 스택과 힙을 너무 단순하게 보지 않기

“지역 변수는 스택, 동적 메모리는 힙”이라는 설명은 시작점으로는 유용하지만 모든 최적화와 저장 영역을 설명하지는 않는다. 첫 사이클에서는 객체 수명과 소유권을 구분하는 데 집중한다.

```text
스택에 만들어진 지역 객체:
  범위를 벗어나면 수명이 끝남

동적으로 확보한 객체:
  소유자가 해제할 때까지 유지됨
```

Node 코드를 읽을 때는 실제 물리적 위치보다 “이 메모리를 누가 언제까지 유효하게 유지하는가”를 먼저 묻는다.
